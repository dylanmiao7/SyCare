这是一套**完整的前端设计交付**：老人本人视角、大字界面，全部基于 `data/` 中的模拟数据。
包含设计文档与一个可直接点击的高保真原型。

> 范围说明：本设计覆盖 [20 小时开发流程](../docs/01_20小时开发流程.md) 中的 8 个页面与所有关键状态；
> **不含**登录、多家庭权限、云端存储与真实 DeepSeek 调用（这些属于后端与导师职责，见 [06 §3](06_无障碍与验收对照.md)）。

## 这个设计的四道底线

整套设计围绕四条不可违反的规则展开，每条都有对应的界面落点与自动化断言。

### 1. 不知道 ≠ 0

`data/` 里血压/脉搏有 26 行空缺，睡眠有 17 行空缺。空缺有三种含义，界面必须一眼可分：

| 数据 | 界面 | 徽标 |
|---|---|---|
| `capture_status = recorded` | `145 / 76` | 本人记录 / 家属代录 |
| `capture_status = not_recorded` | `—` | `○ 未记录`（灰）→ 提示「可以补量一下」 |
| `capture_status = device_error` | `—` | `⚠ 设备错误`（黄）→ 提示「可以再量一次，或检查血压计」 |
| `sleep_hours` 为空 | `—` | `○ 未记录`，**不继承**设备错误 |
| `mood_response = 跳过` | `这次没回答` | `○`（中性灰），**绝不是「不太好」** |

代码层面用 `bpDisplay()` 作为唯一入口，让「空值当 0」在结构上不可能发生。

### 2. 心情跳过不产生任何负面反馈

「不回答」与「很好 / 一般 / 不太好」同尺寸、同色权重。跳过不弹窗挽留、不标红、不写「漏记」。
心情**不画趋势曲线**——心情字段不是心理量表，画曲线等于过度解读。

### 3. 「想找人聊聊」只是意愿

`wants_to_talk = 愿意` 不触发任何通知。界面只显示「需要的话可以联系 {支持对象}」，
**没有发送按钮**，也没有任何后台通知逻辑。

### 4. 未确认的病历文字不进问答

上传的文件状态为「未确认」，页面上明确写着「图片里的文字还没人核对过，暂时不会当成事实回答」；
问答在三类情况下会主动说不知道，并对用药问题引导到医生。

## 一处需要导师拍板的设计取舍

`SYN-003`、`SYN-009`、`SYN-012` 的 30 天记录**全部是家属代录**，但其中包含
`mood_response`（SYN-003 有 20 天「不太好」）和 `wants_to_talk`（20 天「愿意」）——
也就是说，**「本人心情」这个主观字段是家属代填的**。

这导出两种相反的产品结论：

| 解读 | 后果 |
|---|---|
| 家属可以代填心情 | 「愿意找人聊聊」可能是家属的意愿，不能当作本人表达，更不能据此联系任何人 |
| 心情只能本人填 | 这 30 条的主观字段都应标为「非本人填写」，界面不应把它当本人想法展示 |

**本设计采取的保守做法**：这类字段旁追加中性徽标 `家属填写`，记录详情里说明
「心情这部分可能不是本人说的」，且**不显示**「可以联系谁」按钮。

如果导师确认「心情只能本人填」，改动集中在记心情页与记录列表两处，详见
[05 §4.3](05_数据模型与隐私规则.md)。
