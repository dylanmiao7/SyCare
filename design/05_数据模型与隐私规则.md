# 05 · 数据模型、缺失值语义与隐私规则

> 本文件是前端与后端之间的**契约**。前端只依赖这里定义的模型；接 Supabase 时替换数据源实现即可，页面不改。

---

## 1. 实体关系

```
patients ──1:N──> daily_checkins      (patient_id)
    └────1:N──> medical_records       (patient_id)
    └────1:N──> uploaded_files        (patient_id)  ← 本期仅内存
    └────1:N──> summary_drafts        (patient_id)  ← 本期仅内存
    └────1:N──> chat_messages         (patient_id)  ← 本期仅内存
```

三张 CSV 表是**唯一权威来源**（`data/README.md`：聊天记录与小结由应用在真实使用时保存，因此不再预放聊天表和小结表）。

## 3. 缺失值语义（本项目最关键的部分）

### 3.1 读数三态

血压/脉搏这一组读数是**同一时刻同一次测量**，因此 `capture_status` 只有一个值，三者要么都有、要么都没有。前端**不得**出现「有高压没低压」的展示（数据里也不存在这种行）。

| `capture_status` | 数据表现 | 界面（数值位） | 徽标 | 后续动作提示 | 进小结 | 进问答 |
|---|---|---|---|---|---|---|
| `recorded` | 三个数值都有 | `145 / 76`·`77 次/分` | `本人记录`/`家属代录` | — | ✅ | ✅ |
| `not_recorded` | 三个都空 | `—` | `未记录`（灰） | `可以补量一下` | ✅ 计入缺失清单 | ✅ 计入「已记录 N 天 / 未记录 M 天」 |
| `device_error` | 三个都空 | `—` | `设备错误`（黄⚠） | `可以再量一次，或检查血压计` | ✅ 计入缺失清单并单独点名日期 | ✅ 同上 |

**硬性约束**

```js
// 前端唯一允许的缺失判定入口
function bpDisplay(row) {
  if (row.capture_status === 'recorded')
    return { text: `${row.systolic_mmhg} / ${row.diastolic_mmhg}`, kind: null };
  return {
    text: '—',                                   // 永远不是 0
    kind: row.capture_status,                    // 'not_recorded' | 'device_error'
  };
}
```

- ❌ 禁止 `row.systolic_mmhg || 0`
- ❌ 禁止 `Number(row.systolic_mmhg)` 得到 `NaN` 后直接渲染
- ❌ 禁止把 `not_recorded` 与 `device_error` 合并成一个「无数据」

### 3.2 睡眠

`sleep_hours` 为空与 `capture_status` **完全独立**。存在 `capture_status='recorded'` 但 `sleep_hours` 为空的行（数据中共 17 条，其中 15 条血压正常）。

| 情况 | 界面 | 徽标 |
|---|---|---|
| 有值 | `6.1 小时` | — |
| 空 | `—` | `未记录`（灰）——**不继承 `device_error`** |

### 3.3 心情与交流意愿

| 值 | 界面文案 | 徽标 | 禁止 |
|---|---|---|---|
| `很好` / `一般` / `不太好` | 原值 | — | — |
| `跳过` | `这次没回答` | 中性灰 | ❌ 显示「不太好」❌ 显示「未填写」❌ 标红 |
| `wants_to_talk = 愿意` | `愿意` | — | ❌ 「已通知家属」❌ 自动弹出建议 |
| `wants_to_talk = 跳过` | `这次没回答` | 中性灰 | 同上 |

> `mood_response` 与 `wants_to_talk` 也各自独立可为空/跳过。

### 3.4 缺失值的三种「语气」

同一份「没有数据」，在三个页面要说不同的话：

| 页面 | `not_recorded` | `device_error` | `跳过` |
|---|---|---|---|
| 记健康（录入） | `当时没量` | `血压计没测出来` | — |
| 健康记录（回看） | `未记录` | `设备错误` | `这次没回答` |
| 复诊小结（给医生） | `8月11日的血压没有记录` | `8月14日设备没测出来` | `有 1 天没有回答心情` |

**语气递进**：录入时是**动作**（可以补），回看时是**状态**（是什么），小结时是**事实**（客观陈述给医生）。三处都不能变成「漏记」「异常」「缺失数据」这类带评判或术语的词。

## 4. 本人记录 vs 家属代录

### 4.1 数据事实

实测 `data/daily_checkins.csv`：每位老人的 `recorded_by_type` **全部相同**。

| `recorded_by_type` | 老人 | 说明 |
|---|---|---|
| `self` | SYN-001/002/004/005/006/007/008/010/011（9 位） | 本人记录 |
| `family` | **SYN-003/009/012**（3 位） | 30 天全部由家属代录 |

### 4.2 界面规则

1. **每条记录必须显示记录人徽标**（`本人记录` / `家属代录`），不可省略——这是「能看出本人或家属代录」验收标准的落点。
2. 家属代录的记录 **本人不可直接改写**：文案 `这条是家人帮忙记的，想改请联系家人`。
3. 家属代录不影响缺失值语义（`capture_status` 照常生效）。

### 4.3 ⚠ 一个需要导师拍板的产品矛盾（设计已如实处理）

**问题**：`SYN-003` 的全部 30 天记录 `recorded_by_type = family`，但其中包含 `mood_response`（20 天「不太好」）和 `wants_to_talk`（20 天「愿意」）。也就是说，**「本人心情」这个主观字段是家属代填的**。而 `SYN-003` 的 `wants_to_talk = 愿意` 有 20 天，是全组最高。

这两种解读会导出相反的产品结论：

| 解读 | 后果 |
|---|---|
| A. 家属可以代填心情 | 那么「愿意找人聊聊」可能是家属的意愿，**不能当作本人的真实表达**，更不能据此联系任何人 |
| B. 心情/交流意愿只能本人填 | 那么 SYN-003 这 30 条的主观字段都应标记为「不是本人填的」，界面**不应**把「愿意」当作本人的想法展示 |

**我的设计选择**：采取更保守的第三方处理——

- 若 `recorded_by_type === 'family'` 且该行含 `mood_response` / `wants_to_talk`，界面在这些值旁**追加一个中性徽标 `家属填写`**，并在记录详情里显示提示：`这一条是家人帮忙记的，心情这部分可能不是本人说的。`
- 该行**不显示**「可以联系谁」按钮（因为无法确认是本人的意愿）。
- 复诊小结里，这类行的心情只计入总数、并在出处中注明来源类型。

> **需要你确认**：如果导师认为「心情只能本人填」，则应改为：家属代录时**心情与交流意愿字段置灰不可填**，CSV 中 SYN-003/009/012 的主观字段在演示时标为「非本人填写」。两种做法我都可以实现，界面改动集中在记心情页与记录列表。

## 5. 隐私与访问规则

### 5.1 本期规则

| 规则 | 实现位置 |
|---|---|
| 无登录，固定为演示老人本人 | 应用启动时读取选定的 `patient_id`（默认 `SYN-001`，可改为 `SYN-003` / `SYN-006` 演示） |
| 记录**不会自动发给任何人** | 设置页常驻说明 + 记心情页说明 |
| `wants_to_talk = 愿意` **不触发任何通知** | 「可以联系谁」只做信息展示，无发送按钮 |
| `sharing_preference = 不分享` 时额外提示 | 健康记录页顶部提示条（SYN-006） |
| 上传的 PDF 文字未经确认不进问答 | `text_status = unconfirmed` 时，问答拒绝引用 |
| 问答不修改记录、不发消息 | 问一问页的「要问医生」只提供跳转小结按钮 |

### 5.2 数据流边界（前端职责）

```
读取方向（只读）:  patients → { 首页, 设置, 小结, 问答, 记心情 }
                  daily_checkins → { 健康记录, 小结, 问答 }
                  medical_records(confirmed_demo) → { 病历页, 小结, 问答 }
                  uploaded_files(unconfirmed) → { 病历页 }  ← 不进 小结 / 问答

写入方向（仅内存）:  记健康 → daily_checkins(新增/覆盖)
                  记心情 → daily_checkins(仅改 3 个心情列)
                  存病历 → uploaded_files(新增)
                  复诊小结 → summary_drafts(新增/覆盖)
                  问一问 → chat_messages(新增)  ← 唯一不写业务数据的功能
```

**禁止的反向流**：问答 → 记录 / 小结 → 记录 / 任何功能 → 自动通知。

### 5.3 免责声明的固定位置

| 声明 | 出现位置 |
|---|---|
| `模拟演示数据 · 未连接真实后端，刷新后新填的记录会丢失` | 全站底部常驻横幅 |
| `请勿上传真实病历` | 存病历页顶部 |
| `这只是根据您的记录整理，不是医生诊断。` | 每条问答回答末尾 |
| `本小结由已有记录自动整理，不是诊断。` | 小结正文末尾 + 打印页脚 |
| `全部是模拟数据，不是真实老人。` | 设置页 |

## 6. 接入 Supabase 时的替换点（本期不实现，仅留接口）

前端只通过一个数据源接口访问数据，因此后续接入不需要改页面：

```ts
interface SyCareDataSource {
  getPatient(patientId: string): Promise<Patient>
  listCheckins(patientId: string, from: string, to: string): Promise<DailyCheckin[]>
  upsertCheckin(input: CheckinInput): Promise<DailyCheckin>
  patchMood(input: MoodInput): Promise<DailyCheckin>      // 只改 3 个心情列
  listRecords(patientId: string): Promise<MedicalRecord[]>
  uploadRecordFile(input: FileInput): Promise<UploadedFile>
  listUploadedFiles(patientId: string): Promise<UploadedFile[]>
  saveSummaryDraft(input: SummaryInput): Promise<SummaryDraft>
  ask(patientId: string, question: string): Promise<Answer>
}
```

实现切换：

| 环境 | 实现 |
|---|---|
| 本期演示 | `MockDataSource`（读 `data/*.csv`，写内存） |
| 接入后 | `SupabaseDataSource`（表 + RLS + 私有 Storage + Edge Function） |

### 未来表结构与访问规则要点（供导师参考）

| 表 | RLS 要点 |
|---|---|
| `patients` | 只能 `select` 自己有权查看的行；`is_synthetic` 行只对演示账号开放 |
| `daily_checkins` | 按 `patient_id` 隔离；**写入时服务端强制写入真实登录用户**（`recorded_by_type` 不能由前端决定） |
| `medical_records` | 按 `patient_id` 隔离；`text_status != 'confirmed_demo'` 的行**不返回给问答接口** |
| `uploaded_files` | 私有 bucket，路径前缀 = `patient_id`，签名 URL 短时效 |
| 问答 | DeepSeek key 只在 Edge Function 环境变量；函数内**再次校验**可访问的 `patient_id`，不信任前端传入 |

> `data/README.md` 已明确：`recorded_by_type` 是模拟标签，**正式应用须记录真实登录用户**。因此接入后该字段由服务端写入，前端只做展示。

## 7. 校验与归一化规则（前端实现清单）

| 字段 | 规则 | 归一化 |
|---|---|---|
| `record_date` | `1990-01-01` ≤ 值 ≤ 演示「今天」 | `YYYY-MM-DD` |
| `systolic_mmhg` | 50—300 整数 | 取整 |
| `diastolic_mmhg` | 30—200 整数 且 `< systolic` | 取整 |
| `pulse_bpm` | 30—220 整数 | 取整 |
| `sleep_hours` | 0—24，最多 1 位小数 | `round(x, 1)` |
| `recorded_by_type` | `self` \| `family` | — |
| `capture_status` | 由输入推断：三项全空 → 用户选的两态之一；有值 → `recorded` | — |
| `mood_response` | 界面「不回答」→ 存储 `跳过` | — |
| `wants_to_talk` | 界面「不回答」→ 存储 `跳过` | — |
| 文件 | `.pdf`/`.jpg`/`.jpeg`/`.png` 且 ≤ 10 MB | — |

**演示「今天」的锚点**：数据截止 `2026-08-30`。原型固定 `TODAY = '2026-08-30'`，并把 `2026-08-30` 定为星期日。所有「今天」相关逻辑（今日状态条、日期上限、小结默认范围）都用这个常量，避免演示时出现「今天没有数据」的矛盾。
